# Contract

What the server, the payload and the page agree on: the routes, the messages, the components other parts of the page call, and the ids and hash every jump uses. Read this rather than render.py or the code.

## Building and running

```
cd spike/prg-server
bun install
bunx vite build --outDir OUT --emptyOutDir
bun run server/index.ts --state STATE.json --data DIR --repo CLONE --static OUT [--github-comments] [--idle-minutes N] [--scripts DIR]
```

`bun run build` type-checks and builds into `build/`, which is the default for `--static`. `--data` is the folder `collect.py` or `stack.py` wrote, `--repo` the clone `git` and `gh` run in, `--scripts` the skill's `scripts/` (found from this folder by default). Run the server in the background; it writes `{port, token, origin, link, pid}` to the state file (mode 0600) and the page is at `link`. Stop it with

```
T=$(python3 -c "import json;print(json.load(open('STATE.json'))['token'])")
O=$(python3 -c "import json;print(json.load(open('STATE.json'))['origin'])")
curl -s -X POST -H "Authorization: Bearer $T" "$O/api/shutdown"
```

Never echo `$T`. After rebuilding the data folder, `curl -s -X POST -H "Authorization: Bearer $T" "$O/api/reload"` loads it again and the page refetches. The server also stops by itself after `--idle-minutes` (60) with nothing connected.

Checks: `bun test`, `bun run typecheck`, `bunx biome check .`.

### Screenshots

`bun tests/shot.mjs STATE OUT_DIR [light|dark] [WIDTH] [HASH]` opens the state file's link plus `HASH` (such as `#12/guide`) in headless Chromium, waits for the tab list and the network, makes the viewport as tall as the page (so the fixed chat bar sits at the bottom) and writes `OUT_DIR/<hash>-<scheme>-<width>.png`. It exits 1 on any console error, page error or CSP violation, and prints them. To script clicks, copy it elsewhere and import Playwright by absolute path: `import { chromium } from "<this folder>/node_modules/playwright/index.mjs"`. Playwright is 1.64.1 (Chromium build 1248).

## The payload

`GET /api/review` returns `ReviewResponse` from `shared/payload.ts`: `{ stack: StackInfo | null, layers: Layer[], renderError: string | null, linear: boolean }`. A `Layer` is exactly what render.py hands the skill's template for one PR, plus three fields the server adds (`id`, `issueKeys`, `capabilities`) and two per file (`lineCount`, `bruBlocks`), minus `newText` and `_split`. A single PR is a stack of one layer with `stack: null`. Every field has a type in `shared/payload.ts`; the ones that aren't obvious:

- `layer.id`: the PR number, or `0` for a branch with no PR. Every per-PR route, anchor, element id and hash uses it.
- `renderError`: render.py's message when it failed (no `guide.json` yet, or a guide with problems). The layers are then the raw `hunks.json`: `sections: []`, `split: null`, `descriptionCheck: null`, `try: []`, and `stack.check: null`.
- `hunk.lines`: `[sign, oldNo, newNo, text]`. `hunk.blocks` are the runs of changed lines as `[start, end)` indexes into `lines`; a block's `noise` says it is formatting only, `reindented` lists lines that only changed indentation. `hunk.noise` is set when every block is noise.
- `hunk.moves`: runs that moved unchanged. `side: "-"` is where the run left (the template folds it to one row with Show them), `side: "+"` where it landed; `to`/`from` is the other hunk's id and `line` the other end's first line (`R12` or `L3`).
- `hunk.sig`: what the hunk changes, independent of position. Reviewed ticks key on it.
- `hunk.fresh`: changed since `meta.lastPass`. `hunk.commits`: indexes into `meta.commits`, only when `meta.commitMap`.
- `hunk.uses`, `usedBy`, `defines`: names connecting hunks within the PR. Across a stack, `stack.links` does that: `{name, from: "11:f4h1", usedIn: ["12:f3h1"]}`.
- `file.noise`: a lock or generated file. `file.category`: implementation, test, docs, generated, lockfile, agent-guidance, localization or assets. `file.risk`: hints such as `auth` or `migration`.
- `file.lineCount`: lines in the new file when the server holds its text (modified and renamed files that aren't noise), else `null`. Gaps can expand only when it isn't null; fetch the lines from the lines route.
- `file.bruBlocks` (`.bru` files only): `{name, open, close}`; line `n` sits in a block when `open < n <= close`. That is what the template's `bruBefore(f, n)` worked out from `newText`; port `bruStep` for the lines after it.
- `sections`: render.py's resolved sections, guide sections first, then `formatting` (hidden unless formatting is shown) and `generated`. `section.files[].hunks` is the part of the file that section shows. `risk` is `""` when there is none.
- `tells[].line` and `annotations[].row` are `"R12"` or `"L3"`, the same form as line element ids. An annotation has `file`, `hunk` and `row` only when it lands on a line in the diff.
- `ready`: the size band, CI counts (`checks`, null without a PR) and whether implementation and tests changed. `meta.lastPass`: the previous build, `fresh` hunks new since it.
- `descriptionCheck`: `checklist` (claims the diff carries out, with hunks), `unsupported`, `missing`, `issue`; any row may carry a `stack` note.
- `stack`: `layers` bottom first (`needsRebase`), `forks`, `links`, `churn`, and `check` (`stack-guide.json`: a summary per layer and `issues` whose `problem` and `fix` are prose with `[phrase](1014:f3h2)` links).

Lookups: `useReview()`, `useLayer(id)` in `src/queries/review.query.ts`; `indexLayer(layer)` in `src/utils/payload.ts` gives `files`, `hunks` (id to `{file, hunk}`) and `owner` (hunk id to section index), built once per payload. `allIssueKeys(review)` and `defaultLayer(review)` are there too.

Text from the payload, GitHub or Linear goes into the page as text or through `<Prose>` or `<Markdown>`, never as HTML.

## The API

All under `/api`. "Either" means the page or the session (bearer token). The page is the cookie the link sets plus the link's code, sent as `x-prg-key` on every call (`src/queries/key.ts` keeps it in the browser's storage for this origin and takes it out of the address bar) and as `?k=` on its socket, plus Origin on writes and sockets. The cookie by itself gets the page's files and the three picture routes, which an `<img>` asks for, and nothing else: cookies go to every port on 127.0.0.1, so another local server can end up holding it. Anything the server fetches from GitHub or Linear it fetches itself; the page only ever talks to the server.

The page refetches on a push. `src/hooks/useLiveSocket.ts` maps `review` to the `review`, `github`, `linear`, `usages`, `lines` and `refs` queries, `messages` to `messages` and `refs` (Claude's replies widen the references), `session` to `session`, `ticks` to `ticks`, and `github` to `["github", layer]` or `["github", "notify"]`.

## Messages and anchors

`shared/messages.ts`. A message is about an `Anchor`:

| kind         | fields                                                                               | label the session sees         |
| ------------ | ------------------------------------------------------------------------------------ | ------------------------------ |
| `line`       | `layer, file, hunk, side: "L"\|"R", line, endLine?` (a line, or a range on one side) | `src/a.ts:R12@abc1234 \| code` |
| `hunk`       | `layer, file, hunk`                                                                  | the path and the hunk          |
| `file`       | `layer, file`                                                                        | the path                       |
| `section`    | `layer, index` (into `layer.sections`, from 0)                                       | `guide section 2, "Title"`     |
| `tell`       | `layer, file, line: "R12"`                                                           | the path, line and flag labels |
| `annotation` | `layer, index` (into `layer.annotations`)                                            | path, line, level and check    |
| `check`      | `layer, name` (checks are live, so the name isn't checked)                           | `the CI check "name"`          |
| `claim`      | `layer, list: "checklist"\|"unsupported"\|"missing"\|"issue", index`                 | the claim's text               |
| `stackIssue` | `index` (into `stack.check.issues`)                                                  | the problem                    |
| `general`    | `layer?`                                                                             | none                           |

The server refuses an anchor the payload doesn't have and stores it as `ResolvedAnchor`: the anchor plus `label`, `detail` (the numbered lines or text the session gets under the label), `path`, `code` (for line and tell), `loc` (the skill's location, `src/a.ts:R12@abc1234`) and `match` (what a reload looks for), all found by the server itself. On a stack the label and `loc` start `#12 `. `NewMessage.anchor` left out means `general`; a follow-up (`replyTo`) always takes its thread's anchor, and so does Claude's reply.

Where a line anchor may sit:

- `side: "L"`: both ends are lines its hunk removes, numbered in the base.
- `side: "R"`: every line from `line` to `endLine` is a head line of its hunk, or an unchanged line outside every hunk of the file that exists at head (the server holds the file's text, so `file.lineCount` isn't null, and the line is no further than `lineCount`). The code for those lines comes from the file's text. That is how a note sits on a line revealed by expanding unchanged lines: the page names it on the hunk beside the gap, or on the hidden hunk that holds it. A deleted file, or one whose text the server doesn't hold, takes notes only on its hunks' lines.
- A note outside the hunks can't go to GitHub, which takes comments only on lines of the diff; the preview lists it as refused.

A message (`Message`) has `id` (`m1`, `m2`...), `from` (`user` or `claude`), `kind` (`note`, held as a draft until the batch is sent, or `chat`, sent at once), `text`, `anchor`, `replyTo` on replies and follow-ups, `status` (`draft`, `sent` while no session is listening, `delivered`), and on a thread's first message `state` and `resolved`, plus `batch` and `sentAt` once sent, `posted` once on GitHub, `at` and `edited`.

A review the user asks Claude for is a set of threads sharing `review.n`: the request, a chat from the user whose answer is Claude's recommendation, and one thread per finding, which Claude starts (`from: "claude"` with no `replyTo`). Review numbers run across the database. `review.seen` is what the finding's file looked like when it was last checked; after a reload, open findings whose file's hunks changed are sent back to the session once to be checked again (`recheckFrame` in `server/format.ts`). `<ReviewButton layer />` and `<ReviewBlock layer />` (`src/components/chat/Review.tsx`) are the button with its effort menu and the list of the newest unarchived review's findings, both in the ready check.

A thread's first message also carries `events`, what happened between its messages in order: `{kind: "step", text, at}` for each line the session said it was doing for that thread (`POST /activity` with `replyTo`; a repeat of the last step is dropped), and `{kind: "note", text, at}` when the session marks it done or declines it, a follow-up reopens it, or a rebuild sends a finding back. The last hundred are kept. A reply from Claude can carry `ask`, one to four `{question, options, multiple?}`, which needs `text` and `replyTo`; the page offers the choices until the user says something after it, and the answer is an ordinary follow-up. `src/components/chat/Timeline.tsx` draws a thread in that order: steps with shadcn's Trace, notes with Marker, questions with Questionnaire. The components copied from shadcn's registry (radix-nova) and adapted to this project's imports, button and tokens are `kbd`, `button-group`, `empty`, `collapsible`, `trace`, `marker`, `questionnaire` and `message-scroller` in `src/components/ui/`; the last two use the `@shadcn/react` package.

`GET /layers/:layer/local` (either caller) answers `LocalChanges` (`shared/local.ts`): `{where, files, truncated?}`, where `files` maps a file id to `LocalEdit[]`, each `{after, gone, add}`: after head line `after`, the lines in `gone` are replaced by those in `add`. The server finds where the layer's branch is checked out with `git worktree list` on `--repo` (the clone or a worktree; `where` is null when it is checked out nowhere) and runs `git diff -U0 <reviewed head sha>` there over the files the review shows (`server/local.ts`), so it covers unpushed commits, a rebase and uncommitted edits alike; it stops at 3,000 changed lines. The page asks for it on the Guide and Diff tabs every eight seconds while in view, under the query key `["local", layer]`. `DiffTable` turns a file's edits into `local` in the diff context: `marks`, the head line that carries each edit's preview button (the first line it changes, or the line it comes after); and, for the edits being previewed, `shown` (by the `R12` they are drawn under) and `hidden` (the head lines they stand in for). `Half` draws the button, `LineExtras` draws a previewed edit's lines as rows marked `data-local`, and `HunkBody` and the opened unchanged lines hide the reviewed rows meanwhile, so the checkout's code shows in place of the reviewed code, one place at a time. Which places are previewed is kept per file card and not between visits. Edits on lines no hunk shows are named above the table.

A thread's `state` says what the session did with it: `open`, `working` (started on it), `done` (changed the code as asked), `answered` (it was a question; the text is the answer) or `declined` (not doing it; the text says why). `done`, `answered` and `declined` settle a thread (`resolved`), and the page folds it to its last answer. The older `{resolved: true}` means `done`. A follow-up from the user reopens a settled thread.

Messages and reviewed ticks are kept in `prg.db`, a SQLite file in the state file's folder (mode 0600) that every review started from that folder shares. `server/db.ts` has the schema: `messages` (`n`, which numbers messages across every review, so `m12` is one message; `pr`; `stack`; and `body`, the `Message` as JSON, with columns generated from it for queries: `id`, `reply_to`, `sender`, `kind`, `status`, `state`, `resolved`, `archived`, `at`, `text`, `review`, `severity`, `layer` and `path`; the anchor itself stays in `body`) and `ticks` (the page's own keys). A thread is kept with the PR it is about, `owner/repo#12`, or `owner/repo@branch` without one (`prKey` in `shared/ticks.ts`), which is the layer its anchor names or the top of the review when it names none, and in a stack with the stack, `owner/repo stack 1022`, by GitHub's number for it (`gh api repos/o/r/pulls/<top> --jq .stack.number`, asked once at start). A reply is kept with its thread. A review loads the threads of its PRs and of its stack, so a thread follows its PR into another review and stays with a stack whose layers change; without the stack's number a thread goes by its PR alone. Each save writes only the messages that changed. What was sent and never reached a session is queued again at start. Ticks are kept by PR, so the same PR in another review shows them. A rebuild's new anchors are written back whether the reload came while the server was up or it starts on the new build. After a reload each thread looks for what it was about by content (a line by its code, nearest to where it was, in a hunk or else unchanged at head; a hunk by `sig`; a section by its title) and moves there; what isn't found keeps its old anchor marked `outdated`.

## The seams

What one part of the page calls in another.

- `<FileCard layer file hunkIds? section? />` (`src/components/diff/`). `file` is the file id; `hunkIds` limits the card to a section's hunks; `section` is that section's index, which keeps the card's element id unique when a file is split across sections and tells the card which section it is in. In the Diff tab a file whose only changes are formatting is a folded card saying so while Formatting is off.
- `<DiffTab layer />` (`src/components/guide/`): the Diff tab, every file in path order with a list to jump from. `<Guide layer />`: the Guide tab, whose Formatting section stays hidden unless Formatting is on.
- Unchanged lines: `GapBody` expands them a step (20 lines) or all at once; `useGapStore.send({card, act, hunk?})` (`src/components/diff/gaps.store.ts`) does the same from a key, for one card by its element id: `up` and `down` a step above or below a hunk, `open` and `close` every gap. A revealed line takes notes like a hunk line, and a thread on an unchanged line opens its gap far enough to show it.
- `<ReviewedTick layer file? hunkIds? section? />`: a card's tick (`file`, and `hunkIds` for part of a file) or a section's (ticked when every card in it is, indeterminate when some). Keys come from `tickKey(layer, file, hunkIds)` in `src/store/ticks.store.ts`, the template's own: `prg:tick:<repo>#<n>:<path>:<sig,sig>`. A whole file's card (`cardTickKeys`) is every part the sections hold, so a tick in either tab shows in the other. The server keeps the ticks (`src/queries/ticks.query.ts`), so they show in every browser on the review; ticks a browser kept in `localStorage` before that go up on its next load. `useCardDone(layer, file, hunkIds?)` is what folds a card. `<ViewMenu layer />`: show (a select from `src/components/ui/select.tsx`, each commit with its author, date, size and share of the diff), layout and formatting.

## Ids, targets and the hash

`src/utils/anchors.ts`, used for every jump:

- Element ids: section `l12-s2` (1-based), card `l12-f3` in the Diff tab and `l12-s2-f3` in a section, hunk `l12-f3h1`, line `l12-f3-R4` or `l12-f3-L4` (an unchanged line has one once its gap shows it). Every card also has `data-card="l12-f3"`. Only the shown tab is mounted, so these are unique.
- Targets, as `parseTarget` reads them: `s2`, `f3`, `f3h1`, `f3:R4` (a line), each optionally prefixed by a layer, `1013:f42h1`. `findTarget(layer, target, section?)` finds the element (a file's card in that section when it has one there); `reveal(element)` opens enclosing `<details>`, scrolls it to the centre and calls `flash(element)`, which sets `data-flash` for 1.6 s (outlined in `globals.css`; motion may animate it) after clearing it everywhere else, since React may have reused an earlier target's element; `revealWhenReady` retries each frame for 3 s.
- `lineKey({hunk, side, line, endLine?})` is `f3h1:R:4`, by a range's last line; `anchorKey(anchor)` is one string per anchor.
- Hash: `#<layer>/<tab>`, such as `#12/guide` or `#0/diff`, kept in step by `useHashSync`, plus an optional target, `#12/guide/f3h1`. The target is the store's `anchor`: `goTo` and a click in a file list set it, a change of layer or tab clears it, and every change is a history entry. The template's forms still work on load and on `hashchange`: `#f3h1`, `#1013:f42h1`, `#p1013`, and its element ids with or without the layer, `#p12-s2`, `#p11-r-f3-R4` (a line), `#p11-h-f3h1-s0` (a hunk), `#p11-c-1-f9` (a card in section index 1). The page opens on the stack's `focus` layer, else the top one, on Overview.

## Styling

`PAGE_COLUMN` in `src/store/view.store.ts` is the page's column, used by `<main>`, the dock and the keys and theme buttons at its top right: the window's width, up to 160rem, on every tab.

A palette (`src/utils/palette.ts`) is a tweakcn theme's colours for both modes, its radius and its fonts, laid over `theme.css` by a style element and `data-palette` on the root; `public/theme-init.js` puts a saved one back before first paint. `src/styles/palettes.ts` is generated by `scripts/palettes.mjs` and loaded only when the menu opens.

`src/styles/globals.css` maps the theme tokens; use `bg-card`, `text-muted-foreground`, `text-success`, `bg-warning/10`, `bg-diff-add` and so on, never raw colours or `dark:`. For a selected state that reads in both themes use `bg-muted text-foreground`: `bg-secondary` is near white in dark. `highlight.js`, `react-markdown` and `remark-gfm` are installed; nothing may load from another host.
